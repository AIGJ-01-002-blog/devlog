# Feature Specification: 글 삭제·휴지통과 내 글 관리 (007-delete-trash-manage)

**Feature Branch**: `007-delete-trash-manage`

**Created**: 2026-10-07

**Status**: Draft

**Input**: User description: "작성자는 글을 지우면 휴지통으로 옮겨져 30일 동안 되살릴 수 있고, 30일이 지나거나 영구 삭제하면 완전히
지워진다. 내 글 관리 화면에서 임시글·발행 글·휴지통 탭, 공개/비공개 필터, 20개씩 더 보기, 상태 표시와 반응 숫자로 자기 글을 관리한다.
상세 규칙은 docs/13-delete-withdraw.md(글 삭제 부분), docs/41-manage-posts.md, docs/42-permission-matrix.md, docs/20-domain-events.md를
따른다."

**관련 기능 ID**: C-POST-5, C-MANAGE-1(001·002에서 남은 탭·필터·더 보기·상태·숫자·버튼 범위)

**선행 기능**: `002-write-publish` (글·작업본·공개 범위 변경·변경 취소, 내 글 관리의 본인 글 규칙은 001)

**우선순위 단계**: MVP 직후 (Tier A 나머지)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 글을 휴지통으로 옮기고 되살린다 (Priority: P1)

작성자가 글을 삭제하면 확인 뒤 휴지통으로 옮겨지고, 그 글은 즉시 어디에서도 보이지 않는다. 휴지통에서 [복구]하면 원래 상태·공개
범위·목록 위치로 돌아온다.

**Why this priority**: 실수로 지운 글을 되살릴 수 있어야 삭제 기능을 안심하고 쓸 수 있다. C-POST-5의 핵심이다.

**Independent Test**: 공개 글을 삭제해 홈·블로그·상세에서 사라지는지(작성자에게도 상세는 없는 글), 휴지통에서 복구한 뒤 같은
목록 위치에 같은 댓글·좋아요 수로 돌아오는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 작성자의 발행 글, **When** [삭제]를 누르면, **Then** "휴지통으로 옮길까요? 30일 뒤 완전히 삭제돼요" 확인창이 뜨고,
   [휴지통으로]를 누르면 옮겨진다.
2. **Given** 휴지통으로 옮긴 글, **When** 누구든(작성자 포함) 상세 주소를 열면, **Then** 존재하지 않는 글과 똑같이 보이고, 홈·블로그
   목록·블로그 글 수에서 빠지며 그 글의 댓글·좋아요도 보이지 않는다.
3. **Given** 휴지통의 글, **When** 작성자가 [복구]를 누르면, **Then** "복구했어요 [발행 글 탭에서 보기]"가 보이고, 상태·공개 범위·
   처음 공개 시각이 그대로라 목록의 원래 위치에 나타난다.
4. **Given** 휴지통의 글, **When** 수정·저장·발행·공개 범위 변경을 시도하면, **Then** 작성자라도 없는 글과 같은 응답을 받는다.
5. **Given** 제목·본문이 모두 빈 임시글, **When** [삭제]하면, **Then** 휴지통을 거치지 않고 바로 완전 삭제되며 "빈 글이라 바로
   삭제했어요"가 보인다.
6. **Given** 이미 휴지통에 있는 글, **When** 다시 삭제 요청을 보내면, **Then** 아무것도 바뀌지 않는다.
7. **Given** 다른 사람의 글, **When** 삭제·복구·영구 삭제 요청을 직접 보내면, **Then** 없는 글과 같은 응답을 받고 글은 바뀌지 않는다.
8. **Given** 글 상세를 보는 작성자, **When** [삭제]를 누르면, **Then** 내 글 관리와 같은 확인창과 처리로 휴지통에 옮겨진다.

### User Story 2 - 영구 삭제하거나 30일 뒤 자동으로 완전히 지워진다 (Priority: P2)

작성자는 휴지통에서 [영구 삭제]로 바로 지울 수 있고, 아무것도 하지 않으면 30일 뒤 자동으로 완전 삭제된다. 완전 삭제되면 그 글에 달린
댓글·좋아요·태그 연결도 함께 지워진다.

**Why this priority**: 데이터가 쌓이지 않게 하고, 지운 글이 정말 지워진다는 약속을 지킨다. 다만 되살리기(P1)가 먼저다.

**Independent Test**: 휴지통의 글을 영구 삭제해 다시 복구할 수 없는지, 삭제한 지 30일이 지난 글이 다음 정리 때 사라지는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 휴지통의 글, **When** [영구 삭제]를 누르면, **Then** "영구 삭제하면 되돌릴 수 없어요. 댓글·좋아요도 함께 지워져요"
   확인창이 뜨고, 확인하면 즉시 완전 삭제된다.
2. **Given** 휴지통에 없는 글, **When** 영구 삭제나 복구 요청을 보내면, **Then** 없는 글과 같은 응답을 받는다.
3. **Given** 휴지통에 옮긴 지 30일이 지난 글, **When** 매일 한 번의 정리 시점이 되면, **Then** 완전 삭제된다.
4. **Given** 완전 삭제된 글, **When** 그 글 번호의 주소를 열면, **Then** 없는 글이며 그 번호는 다른 글에 다시 쓰이지 않는다.
5. **Given** 완전 삭제된 글이 쓰던 사진, **When** 다른 글에서 쓰지 않으면, **Then** 연결이 끊긴 것으로 기록되어 7일 뒤 정리된다.

### User Story 3 - 내 글 관리에서 탭과 필터로 내 글을 훑는다 (Priority: P3)

작성자는 `/manage/posts`에서 [임시글] [발행 글] [휴지통] 탭과 각 탭의 글 수를 보고, 한 줄 목록으로 20개씩 훑으며 [더 보기]로 이어
본다. 발행 글은 [전체] [공개] [비공개]로 거를 수 있다.

**Why this priority**: 글이 많아질수록 필요한 관리 화면이다. 삭제·복구 버튼이 놓일 자리이기도 하다.

**Independent Test**: 임시글·공개·비공개·휴지통 글을 섞어 21개 이상 만든 뒤, 탭별 개수·정렬·필터·[더 보기]가 맞고 같은 글이 두 번
나오지 않는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인한 작성자, **When** `/manage/posts`에 들어가면, **Then** 기본으로 [임시글] 탭이 열리고 탭마다 `임시글 3 · 발행 글 24 ·
   휴지통 1`처럼 글 수가 보인다.
2. **Given** 임시글·발행 글 탭, **When** 목록을 보면, **Then** 마지막 수정 시각 최신순(같으면 나중에 만든 글 먼저)이고, 휴지통 탭은
   삭제 시각 최신순이다.
3. **Given** 어느 탭이든 글이 20개를 넘음, **When** [더 보기]를 누르면, **Then** 다음 20개가 이어 붙고 같은 글이 두 번 보이지 않는다.
4. **Given** 목록을 보는 사이 다른 탭에서 자동 저장으로 어떤 글의 수정 시각이 바뀜, **When** [더 보기]를 누르면, **Then** 이미 보인 글은
   다시 나오지 않는다.
5. **Given** [발행 글] 탭, **When** [공개]나 [비공개] 필터를 고르면, **Then** 맞는 글만 보이고 주소에 필터가 남는다.
6. **Given** 비회원, **When** 내 글 관리에 들어오면, **Then** 로그인 화면으로 가고 로그인 후 이 화면으로 돌아온다.

---

### User Story 4 - 각 글의 상태와 숫자를 보고 그 자리에서 처리한다 (Priority: P4)

각 줄에는 상태(임시·🌐 공개·🔒 비공개·수정 중·숨김)와 날짜, 발행 글의 조회수·좋아요·댓글 수가 보이고, 버튼을 누르면 화면을 새로
고치지 않고 그 줄만 바뀐다.

**Why this priority**: P3의 목록을 실제 관리 도구로 만든다.

**Independent Test**: 각 상태의 글을 준비해 배지·날짜·숫자·버튼 구성이 탭별 규칙과 같은지, 각 버튼이 그 줄만 바꾸는지 확인한다.

**Acceptance Scenarios**:

1. **Given** [임시글] 탭, **When** 목록을 보면, **Then** 각 줄에 제목(비어 있으면 회색 "(제목 없음)"), "마지막 저장 10월 3일 14:03"
   (24시간 이내는 "N분 전"), [이어 쓰기] [삭제]가 있고 공개 범위는 보이지 않는다.
2. **Given** [발행 글] 탭, **When** 목록을 보면, **Then** 제목 앞에 🌐/🔒(화면 읽기 프로그램용 "공개"/"비공개" 글자 포함), 작업본이
   있으면 [수정 중] 배지, "발행 2026.10.01 · 수정됨 10월 3일", 👁 조회수 ♥ 좋아요 💬 댓글이 보인다.
3. **Given** 발행 글, **When** 버튼을 보면, **Then** [보기] [수정] [공개 범위 ▾] [삭제]가 있고, 수정 중이면 [수정] 대신 [이어서 수정]
   [변경 취소]가 있다.
4. **Given** [휴지통] 탭, **When** 목록을 보면, **Then** 탭 위에 "휴지통의 글은 30일 뒤 자동으로 완전히 삭제돼요"가 있고, 각 줄에
   "(임시글이었음)"/"(발행 글이었음)", "삭제 10월 2일 · 27일 뒤 완전 삭제", [복구] [영구 삭제]가 있다.
5. **Given** 비공개 글, **When** [공개 범위 ▾]로 공개를 고르면, **Then** "모든 사람이 볼 수 있게 돼요" 확인 뒤 배지만 바뀌고 "수정됨"은
   생기지 않는다. 공개 → 비공개는 확인창 없이 바뀐다.
6. **Given** 수정 중인 발행 글, **When** [변경 취소]를 누르면, **Then** "수정 중인 내용을 버리고 발행된 글로 되돌릴까요?" 확인 뒤
   [수정 중] 배지가 사라진다.
7. **Given** 아무 버튼, **When** 처리가 끝나면, **Then** 화면 전체를 새로 고치지 않고 그 줄과 탭 개수만 바뀐다(삭제하면 휴지통 개수 +1).
8. **Given** 처리 실패(예: 이미 휴지통에 있는 글), **When** 응답을 받으면, **Then** 그 줄 아래에 이유가 보이고 목록을 다시 불러온다.

### Edge Cases

- 휴지통으로 옮기는 순간 서버에 잠시 보관 중인 자동 저장분이 있으면? → 영구 저장소에 반영한 뒤 옮겨, 복구했을 때 마지막 내용이 남아 있다.
- 휴지통으로 옮긴 발행 글이 수정 중이었다면? → 작업본도 그대로 보존되어 복구하면 수정 중 상태로 돌아온다.
- 같은 글에 삭제·복구·영구 삭제 요청이 동시에 오면? → 한 번에 하나씩 처리되어 상태가 꼬이지 않는다.
- 이메일 인증 전 회원이 자기 글을 삭제·복구·영구 삭제하면? → 허용된다(지우는 것은 남에게 해가 되지 않는다).
- 관리자가 남의 글을 지우려 하면? → 없는 글과 같은 응답이다. 관리자는 삭제가 아니라 숨김만 한다(Tier C).
- 관리자가 숨긴 글은 내 글 관리에서? → 작성자에게 "운영 정책에 따라 숨겨짐" 배지와 함께 보인다.
- 완전 삭제되는 글에 대기 중인 신고가 있으면? → 그 글과 그 글 댓글의 대기 중 신고는 "대상 없음"으로 종료된다(신고 기능이 들어온 뒤).
- 완전 삭제되는 글의 태그는? → 글과의 연결만 지우고 태그 자체는 남긴다.
- 주소나 요청에 다른 사용자 값, 큰 목록 크기 값을 넣으면? → 무시되고 본인 글 20개씩만 나온다.
- 잘못된 [더 보기] 위치 값을 보내면? → 거부되고 이유가 안내된다.
- 탭을 바꾸거나 필터를 바꾸면? → 그 탭·필터의 첫 20개부터 다시 보인다.

## Requirements *(mandatory)*

### Functional Requirements

**휴지통으로 옮기기 (docs/13 §2, D-1~D-3)**

- **FR-001**: 작성자는 임시글과 발행 글을 확인창("휴지통으로 옮길까요? 30일 뒤 완전히 삭제돼요")을 거쳐 휴지통으로 옮길 수 있어야 한다.
  [삭제]는 내 글 관리와 글 상세(작성자에게만 보임) 두 곳에 있어야 한다.
- **FR-002**: 제목·본문이 모두 빈 임시글은 휴지통을 거치지 않고 바로 완전 삭제하고 "빈 글이라 바로 삭제했어요"를 안내해야 한다.
- **FR-003**: 휴지통으로 옮기면 즉시 상세(작성자 포함)가 없는 글과 같은 응답이 되고, 홈·블로그·태그·검색·sitemap 목록과 블로그 글 수에서
  빠지며, 그 글의 댓글·좋아요도 보이지 않아야 한다. 이는 001·003의 공용 목록 조건과 읽기 판정에 "휴지통 글 제외"가 처음부터 들어 있는
  것으로 보장해야 한다.
- **FR-004**: 휴지통에 있는 동안 글의 상태·공개 범위·처음 공개 시각·댓글·좋아요·태그·사진 연결·작업본·반응 수는 그대로 보존해야 한다.
- **FR-005**: 휴지통으로 옮기기 직전에 서버에 잠시 보관 중인 자동 저장분을 영구 저장소에 반영해야 한다.
- **FR-006**: 휴지통 글에 대한 자동 저장·수동 저장·수정·발행·공개 범위 변경은 작성자라도 없는 글과 같은 응답으로 거부해야 한다.
- **FR-007**: 이미 휴지통에 있는 글을 다시 삭제하면 아무것도 바꾸지 않아야 한다.

**복구 (docs/13 D-4)**

- **FR-008**: 작성자는 휴지통의 글을 복구할 수 있어야 하며, 복구하면 원래 상태·공개 범위·처음 공개 시각 그대로 돌아와 목록의 원래
  위치에 나타나야 한다(맨 위로 올라오지 않는다). 휴지통에 없는 글의 복구 요청은 없는 글과 같은 응답이어야 한다.

**완전 삭제 (docs/13 §2-5, D-5)**

- **FR-009**: 영구 삭제는 휴지통에 있는 글에만 할 수 있어야 하며, 확인창("영구 삭제하면 되돌릴 수 없어요. 댓글·좋아요도 함께
  지워져요")을 거쳐 즉시 완전 삭제해야 한다.
- **FR-010**: 휴지통에 옮긴 지 30일이 지난 글은 매일 한 번 자동으로 완전 삭제해야 하며, 여러 서버에서 중복 실행되지 않아야 한다.
- **FR-011**: 완전 삭제하면 글과 그 글의 댓글(다른 사람이 쓴 것 포함)·좋아요·태그 연결·사진 연결·작업본을 함께 지워야 한다. 태그
  자체는 남긴다.
- **FR-012**: 완전 삭제된 글이 쓰던 사진은 다른 글에서 쓰지 않으면 연결이 끊긴 것으로 기록해 7일 뒤 사진 정리 대상이 되게 해야 한다.
- **FR-013**: 완전 삭제할 때 그 글과 그 글 댓글에 걸린 대기 중 신고 사건은 처리한 관리자 없이 "대상 없음"으로 종료하고 처리 일자를
  기록해야 한다(신고 기능이 있을 때).
- **FR-014**: 글 번호와 주소는 완전 삭제 뒤에도 다시 쓰지 않아야 한다.

**권한 (docs/42 §5-2, docs/13 §2-3)**

- **FR-015**: 삭제·복구·영구 삭제는 작성자만 할 수 있어야 하며, 남의 글이면 관리자라도 없는 글과 같은 응답을 주고 글은 바뀌지 않아야
  한다. 이 검사는 서버에서 매 요청마다 하고, 같은 글에 대한 요청은 한 번에 하나씩 처리해야 한다.
- **FR-016**: 비회원의 삭제·복구·영구 삭제 요청은 로그인 필요로 거부해야 하고, 이메일 인증 전 회원의 자기 글 삭제·복구·영구 삭제는
  허용해야 한다.

**사건 연동 (docs/20 §3)**

- **FR-017**: 상태가 실제로 바뀐 경우에만, 처리가 확정된 뒤 휴지통 이동(`PostTrashed`: 글·작성자·이동 시각), 복구(`PostRestored`: 글·
  작성자·복구 시각), 완전 삭제(`PostPurged`: 글·작성자, 영구 삭제·30일 경과·탈퇴 정리 모두)를 한 번씩 알려야 한다. 사건에는 제목·본문
  같은 글자를 넣지 않는다. 사건 처리가 실패해도 삭제·복구 자체는 성공해야 한다.

**내 글 관리 목록 (docs/41 §1~§3·§5, M-1~M-10)**

- **FR-018**: 내 글 관리(`/manage/posts`)는 [발행 글] [임시글] [휴지통] 탭을 두고 기본 탭은 [발행 글]이어야 하며(2026-10-14 민서님 요청으로 [임시글]에서 바꿈), 로그인한 본인의 글만
  보여야 한다(주소·요청의 다른 사용자 값은 무시).
- **FR-019**: 각 탭에 글 수를 보여줘야 한다. 글 수는 첫 화면에서만 계산하고 [더 보기] 때는 다시 계산하지 않는다.
- **FR-020**: 정렬은 임시글·발행 글은 마지막 수정 시각 최신순(같으면 나중 글 먼저), 휴지통은 삭제 시각 최신순이어야 한다.
- **FR-021**: 목록은 카드가 아닌 한 줄 목록이며, 세 탭 모두 20개씩 [더 보기]로 이어 붙여야 한다. 요청한 개수 값은 무시하고, 이미
  화면에 있는 글은 다시 붙이지 않아야 한다. 잘못된 이어 보기 위치 값은 거부해야 한다.
- **FR-022**: [발행 글] 탭에는 [전체] [공개] [비공개] 필터를 두고 선택이 주소에 남아야 한다.
- **FR-023**: 탭별 표시는 docs/41 §3을 따라야 한다: 임시글(제목 또는 "(제목 없음)", 마지막 저장 시각·24시간 이내 "N분 전", 공개 범위
  없음), 발행 글(🌐/🔒와 화면 읽기용 글자, [수정 중] 배지, 발행일·"수정됨" 날짜, 조회수·좋아요·댓글 수, 숨긴 글 배지), 휴지통(원래 상태
  "(임시글이었음)"/"(발행 글이었음)", 삭제일·완전 삭제까지 남은 날, 탭 위 30일 안내).
- **FR-024**: 목록은 글 본문을 읽거나 내려보내지 않아야 하며, 응답 시간은 300ms 이내여야 한다.

**내 글 관리 버튼 (docs/41 §4)**

- **FR-025**: 버튼은 탭과 상태별로 docs/41 §3·§4를 따라야 한다: 임시글 [이어 쓰기] [삭제], 발행 글 [보기] [수정](수정 중이면 [이어서
  수정] [변경 취소]) [공개 범위 ▾] [삭제], 휴지통 [복구] [영구 삭제], 화면 위 [새 글].
- **FR-026**: [공개 범위 ▾]는 비공개 → 공개일 때만 "모든 사람이 볼 수 있게 돼요" 확인창을 띄우고, 다시 발행 없이 바로 바꿔 "수정됨"을
  남기지 않아야 한다(002 규칙). [변경 취소]는 "수정 중인 내용을 버리고 발행된 글로 되돌릴까요?" 확인 뒤 작업본만 지워야 한다.
- **FR-027**: 모든 처리는 화면 전체를 새로 고치지 않고 그 줄과 탭 개수만 바꿔야 하며, 실패하면 그 줄 아래에 이유를 보여주고 필요하면
  목록을 다시 불러와야 한다. 복구하면 "복구했어요 [발행 글 탭에서 보기]"를 보여줘야 한다.

### Key Entities *(include if feature involves data)*

- **글(Post)**: 002에서 정의. 이번에 삭제 일자(비어 있으면 정상, 있으면 휴지통)를 쓴다. 삭제 일자는 상태(임시·발행)·공개 범위와 별개다.
  조회수·좋아요 수·댓글 수는 `post_stat` 뷰로 센 값을 보여준다(V3 정규화, 글에 저장하지 않는다).
- **작업본(PostDraft)**: 002에서 정의. 휴지통에서도 보존하고, 완전 삭제 때 함께 지운다. 목록의 [수정 중] 배지 근거다.
- **사진 연결·태그 연결·댓글·좋아요**: 휴지통에서는 그대로, 완전 삭제 때 함께 지운다(사진 파일과 태그 자체는 각각의 정리 규칙을 따른다).
- **신고 사건**: 완전 삭제 때 대기 중이면 "대상 없음"으로 종료한다. 기록 자체는 남는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 삭제한 글은 모든 목록·상세·검색·sitemap에서 즉시 사라지고(작성자에게도 상세는 없는 글), 휴지통에서만 보인다(노출 0건).
- **SC-002**: 복구 전후로 상태·공개 범위·목록 위치·댓글·좋아요 수가 달라지는 경우가 0건이다.
- **SC-003**: 30일이 지나거나 영구 삭제한 글과 그 댓글·좋아요·태그 연결이 다음 확인 때 남아 있는 경우가 0건이고, 사진은 정리 대상이
  되며, 대기 중 신고는 "대상 없음"으로 종료된다.
- **SC-004**: 빈 임시글 삭제는 100% 휴지통을 거치지 않는다.
- **SC-005**: 남의 글에 대한 삭제·복구·영구 삭제 요청은 100% 없는 글과 같은 응답이고 글은 바뀌지 않는다.
- **SC-006**: 글 100개가 있는 작성자가 [더 보기]를 끝까지 눌러도 각 글이 정확히 한 번씩 보이고, 각 목록 응답은 300ms 이내다.
- **SC-007**: docs/13 §5 C-POST-5 공통 완료 기준 1~5와 docs/41 §7 공통 완료 기준 1~8이 모두 자동 테스트로 확인된다.

## Assumptions

- **A-1**: 회원 탈퇴 데이터 처리(docs/13 §3, 30일 유예·익명 처리)는 020이 맡는다. 이 spec은 글 삭제와 그 완전 삭제 절차를 만들고,
  020이 탈퇴 정리 때 같은 완전 삭제 절차를 다시 쓴다.
- **A-2**: 댓글·좋아요·조회수·태그·사진은 Tier B다. 그 전에는 숫자가 0으로 보이고, 함께 지울 댓글·좋아요·태그·사진 연결이 없을 뿐 규칙은
  처음부터 같다.
- **A-3**: 관리자 숨김(배지)과 신고 사건 종료는 Tier C 기능이 들어올 때 동작한다. 목록·완전 삭제 규칙에는 처음부터 자리를 둔다.
- **A-4**: 내 글 관리의 검색·여러 글 한 번에 처리는 개인 확장으로 범위 밖이다.
- **A-5**: 001의 "본인 글만·빈 상태·비회원 로그인 이동" 규칙과 002의 공개 범위 변경·변경 취소 동작은 그대로 쓴다.
- **A-6**: docs/41 문서 상태가 "초안(항목 확인 중)"이지만, 결정 사항 M-1~M-10과 공통 완료 기준을 확정된 것으로 보고 옮겼다.
